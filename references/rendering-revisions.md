# 渲染、增量修订与交付

## 渲染路径

### 已有图稿

先检查已有 SVG、PPTX、绘图脚本和最后接受的预览。修改原有可编辑源，不为一次局部修改重建整套拓扑。

### 新的精确方法图

张量维度、公式与数学连接较多时，采用确定性 SVG、原生 PPTX 对象或可复现的科学绘图代码。保留 live text、独立连接线、矩阵单元或逻辑分组。PDF 从矢量源导出，PNG 从同一源渲染。

如果宿主只有位图生成能力，明确交付的是概念草案；精确公式和维度必须在输出检查中逐一核对，不能宣称其为可编辑源。

### 风格探索与位图

用户要求视觉风格探索、图像编辑或位图时，按可用图像工具及宿主要求操作。给工具的内容以已确认计算清单为准，限制生成器自行添加分支/结果。

不硬编码某个图像模型名称。只有工具明确返回或配置可核实时，才报告实际使用的模型。

已有任务授权覆盖的常规修改直接完成，不额外设置固定的“生成后必须再确认”流程。尚未获得的外部上传/发布授权仍按宿主规则处理。

## 修订前保存什么

在工作笔记中列出当前正确要素，例如：

`保留：双路线、各自输出、输入网格、RBF 曲线、维度、模块 ID、论文参考映射。`

`本次修改：在融合处区分矩阵乘法与逐元素乘法。`

若项目已有版本控制，使用正常差异记录即可。不要为每一次调整生成新的 final-v2-final3 文件。用户已有备份策略时遵循其策略。

## 针对常见反馈的正确处理

| 用户反馈 | 应修改 | 同时保留 |
|---|---|---|
| “看不出数据格式和维度变化” | 补矩阵/张量表示、轴、边界和关键中间 shape | 已确认拓扑、核心模块、运算节点 |
| “中间过程可视化” | 展开真实的选择 mask、基函数、特征贡献或 token 转换 | 不捏造模型没有的选择器/注意力 |
| “连接要体现数学逻辑” | 操作数分别接算子，标广播与聚合轴 | 输入输出、已有数据图形和维度 |
| “两张图需要层级” | 建立相同 ID 与接口，总览显示模块，细节展开内部 | 任务独立性、分支关系、训练边界 |
| “为什么有这么多版本” | 给出当前规范文件，说明预览/源文件关系 | 不删除用户原文件，不再主动分叉方案 |
| “不改图，只解释” | 读取依据，解释任务/模块/公式 | 图文件与生成脚本保持不变 |
| “给模块起独有名字” | 提供机制一致的中英文候选名，必要时检索同名 | 不自动改图，不把命名当原创证明 |

## 最终 QA

只检查本任务相关项，出现真实错误再迭代：

- [ ] 模型版本、输入、任务输出与来源一致。
- [ ] 两张主图的模块 ID 与接口对应，未引入虚假的串行/融合。
- [ ] 主张对应的核心模块在总览可见。
- [ ] 维度和数据图形同时可读，堆叠轴含义正确。
- [ ] 矩阵乘法、Hadamard、加法、拼接、缩放没有混淆。
- [ ] 分支实际相交处没有误合并；每个操作数进入正确端口。
- [ ] 训练监督与推理数据流不同，损失不连接为预测输出。
- [ ] 修改前正确的内容未丢失。
- [ ] 在实际尺寸预览，文字、连线、图例无明显遮挡或截断。
- [ ] 对外称可编辑的源文件确实有可编辑对象，而不是嵌入整页 PNG。

两次小修仍未解决布局问题时，调整布局/拆分细节面板。方法事实缺失时询问必要信息，不靠更多渲染猜测。

## 文件与最终回复

默认保持两套同内容文件：overview 的源/预览，以及 modules 的源/预览。用户只需要 PNG 时可以只交 PNG；已有文件名优先沿用。

交付说明包括“改了什么”“现在哪份是当前版”“源文件在哪”。用户若只讨论，直接回答问题，不列没有修改的文件清单，也不启动绘图。

GitHub 发布、向协作工具写入、替换共享文件等动作需要明确任务授权；准备可上传文件本身不意味着已获发布授权。
